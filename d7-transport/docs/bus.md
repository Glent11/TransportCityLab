## 4. Идемпотентная обработка
Если событие придет дважды, система не выполнит двойную работу. Это обеспечено двумя механизмами:
1. Дедупликация по id: в файле `processed.jsonl` хранятся id всех обработанных событий. Если id уже есть, консьюмер отклоняет событие с причиной `duplicate`.
2. В самой функции обработки (handle) используется операция «поставить» (перезапись по ключу application_id), а не «добавить». Даже если дедупликация пропустит событие, состояние не изменится.

## 6. Хаос-эксперимент
Прогноз: При выключении брокера на 2 минуты продюсер сохраняет события в локальную очередь (spool/), после включения — доставляет их.
Факт: Проверка №7 подтвердила это. При выключенном брокере событие ушло в очередь недоставленных, после включения доставлено ровно один раз.
Слабое место: Очередь spool/ может расти бесконечно, если брокер не поднимется. План закрытия: ограничить количество попыток (10) и писать service.error.

## 7. Ответы на три вопроса
1. Почему подпись по канонической строке, а не по готовому JSON? 
 JSON не гарантирует порядок полей и пробелы. Каноническая строка жестко фиксирует формат, чтобы отправитель и получатель получили одинаковый хэш.

2. Брокер упал на 10 минут: какие гарантии есть и каких нет?
 Даёт гарантию «хотя бы один раз» (события копятся в spool/ при падении брокера). Не даёт «ровно один раз» (поэтому нужна дедупликация на консьюмере). События, которые продюсер не успел создать до падения, теряются.

3. fee.paid пришло повторно через час с тем же id и свежим time: атака или авария?
Это авария (баг продюсера). Атака исключена, так как злоумышленник не смог бы подделать time без ключа. Консьюмер отбросит событие по проверке дедупликации (причина duplicate), повторной обработки не будет.
